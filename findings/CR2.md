- **CR2-1** — **Impact:** Every invocation through these popup operations fails with the updated bridge pair. Reapproval and reload do not repair the mismatch; editing within the runtime is a workaround. Snapshot inspection and All sites storage operations remain functional. **Invariant:** The selected FP1 contract preserves trusted-origin site writes and Try, and preserves origin-checked site clearing without approval. **Checked:** `syncedState.tsx` supplies `expectedOrigin`; the content listener validates it, but omits it from all three page-bound payloads at lines 108–112, 134, and 154. Runtime guards at lines 73, 100, and 124 reject missing values. Neither the relay helper nor another caller adds the field. **Proof:** Executed `node .context/extension-review-repro.cjs` with actual transpiled content and runtime bridge modules and a simulated browser/window transport. All three operations returned `{ok:false,reason:"blocked"}`; no write or clear ran. A direct runtime write carrying the origin succeeded as a positive control. This is controlled integration evidence, not a real extension browser run. **Fix:** Forward the validated expected origin in every page-bound operation and test both production bridge endpoints together. **Gate:** Blocks because core popup operations fail unconditionally within their supported workflow.

- **CR2-2** — **Impact:** Opening, copying a path, and building an AI prompt can use a fabricated path for a Next.js fallback result. Removing the configured root avoids the demonstrated double prefix but affects other path resolution. This requires the Next dev-server fallback, a relative response, successful root recovery, and a nonempty configured root; population prevalence is unknown, with F2 provisional for that combination. **Invariant:** FP5 requires a resolved absolute filename to retain its provenance through all action consumers. **Checked:** `resolveNextjsRelativePath()` returns `{fileName, pathKind:"absolute"}`, including its cached-root path. Its caller keeps only `fileName` and derives the new kind from the original relative response. `getFiberLabel()` carries that incorrect kind to `buildLink()`, while `resolveSourcePath()` handles explicit project-relative paths before its existing under-root check. Direct absolute API responses and failed root recovery do not demonstrate this regression. The same action-input invariant reaches `performAction.ts:45`, `buildPrompt.ts:21`, and tree source conversion; the resolver is the correction point. **Proof:** Ran the scratch Vitest test `.context/runtime-review/path.test.ts` through actual `resolveSourceFromFiber → getFiberLabel → buildLink`, mocking only fetch responses. It failed: expected `vscode://file//repo/app/page.tsx:10:5`, received `vscode://file//repo/repo/app/page.tsx:10:5`. On the base, the absence of the new incorrect kind lets the under-root check retain the original absolute path. **Fix:** Keep the filename and provenance returned by root recovery together instead of reconstructing the kind from the pre-resolution filename. **Gate:** Blocks because the change breaks the primary source-opening workflow for a supported Next.js resolution path.

- **CR2-3** — **Impact:** A revoked origin can observe new private configuration after the removal event has propagated. Reloading the affected document after revocation recovers; disclosed values cannot be recalled. This needs a delayed initial response crossing revocation, so F3 is provisional and prevalence unknown. **Invariant:** FP1 allows previously disclosed data to remain known but requires subsequent sharing to stop after revocation propagation, including stale-initialization protection. **Checked:** During initialization, `currentAccess.origin` is null, so the grant-change listener ignores the event. The delayed response then unconditionally installs its stale approval. Normal revocation after initialization refreshes access; localhost's intentional trust exception is unrelated. **Proof:** Executed `.context/extension-review-repro.cjs` against the production content entry with simulated browser APIs. Delivered a grant-removal event before resolving a pending approved identity response. No refresh occurred (one identity request total), and a later configuration update containing `/private/added-after-revoke` appeared in the page dataset. This proves new disclosure, beyond the accepted limit for previously exposed data. **Fix:** Track trust changes during initialization and prevent stale responses from committing approval; resolve current approval before publishing when initialization crossed a relevant change. Apply the same ordering rule to overlapping refreshes. **Gate:** Blocks because revocation is the selected confidentiality boundary and this implementation can ignore it after propagation. This does not inherit CR1's broader historical S0 rating: the demonstrated reach is narrower.

- **CR2-4** — **Impact:** A user who opens Customize link template and then wants to leave setup encounters silent dead controls. Escape restores navigation, so recovery is readily available; F2 describes the occasional decision to abandon a custom draft, not all onboarding sessions. **Invariant:** FP3 explicitly allows Back/Skip to abandon idle editing while preventing navigation during persistence. **Checked:** `EditorPicker` reports `editing() || saving()` as one pending value; both navigation handlers reject that value, while Wizard disables Back/Skip only for `writePending()`. The callbacks therefore reject a state the controls present as available. **Proof:** Rendered the real WelcomeScreen, Wizard, and EditorPicker in `.context/runtime-review/onboarding.test.tsx` with a successful storage stub. Opened customization, asserted Skip was enabled, clicked it, and observed zero close calls (failing assertion). The reviewer's companion Escape-then-Skip counterexample passed. Back shares the inspected early-return guard; its behavior was not separately clicked in the reproduction. **Fix:** Distinguish a save in progress from an unfinished idle draft for navigation. Allow explicit abandonment while retaining pending-editor validation for Continue/Finish. **Gate:** Non-blocking on its own because canceling the draft recovers, but it is a concrete regression in the chosen navigation contract.

- **CR2-5** — **Impact:** The settings E2E invocation deterministically fails before verifying dismissal/reset persistence. Chromium was executed; the other configured browsers use the same test but were not run. **Invariant:** Project instructions require named E2E gates to validate supported workflows, and FP3 explicitly calls for selecting an editor in this existing test. **Checked:** The scenario starts with an empty editor, reaches Pick your editor, and immediately clicks Continue. The new disabled state is correct product behavior; increasing the timeout cannot repair the test. **Proof:** Ran `PORT=46000 . ./scripts/dev-ports.sh && E2E_GROUP=settings pnpm --dir apps/playwright exec playwright test tests/libs/settings.spec.ts --grep 'welcome dismissal survives' --project=chromium` under the Node version from `.nvmrc`, using a checked free port block and Playwright-owned servers. It failed after 30 seconds at line 292 waiting for the disabled Continue button. The failure artifact includes the Pick your editor snapshot and disabled control. **Fix:** Select and successfully persist an editor before continuing, and preserve the later dismissal/reset assertions. **Gate:** Blocks because a required E2E scenario now fails on the candidate. Do not remove the new selection requirement to satisfy the old fixture.
